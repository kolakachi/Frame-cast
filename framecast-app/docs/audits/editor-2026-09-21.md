# Editor frontend/backend audit — 21 September 2026

Scope: editor autosave, export input selection, render jobs, export actions, public shares, approvals and scheduling. Static code review plus isolated automated tests and browser checks with mocked APIs. This is not a production rendering, provider, or social publishing test.

## Implemented in this change

- Open, Download, Schedule, Send for approval and Share publicly now check whether the selected export includes saved edits. Unsaved/pending editor changes also trigger the warning.
- Users can cancel, explicitly use the previous video, or update and continue. The latter saves pending edits, queues an export, waits for that exact job, checks for edits during rendering, then continues. Failed saves/renders do not automatically deliver an old file.
- New export jobs capture a fingerprint of the project and ordered scene render inputs at queue time. The workspace-scoped freshness endpoint compares current inputs with that fingerprint. Older exports use a conservative save-time comparison; they can produce extra warnings.
- Schedule and approval dialogs retain the export selected by the action, rather than switching implicitly as newer jobs arrive.
- Open/download controls are buttons so middle-click cannot bypass the warning.
- Audio-volume autosaves retain the original scene ID. Export waits for pending audio, music, motion and audiogram saves; caption flush preserves the drafted highlight color.
- Additive migration: `2026_09_22_010000_add_export_source_fingerprint.php`. Run during deployment. No existing project/export/media data is deleted by this migration. The project-216 automatic-finishing cutoff is unchanged.

## Remaining findings, in priority order

### P1 — Render jobs read mutable scene data

`api/app/Jobs/RenderSceneSegmentJob.php::handle` reloads Scene and Project when each queued segment runs. `ConcatenateExportJob` also uses current project data. If a user edits or removes scenes while jobs are running, segments can represent different revisions, or rendering can fail. A fingerprint detects that edits happened; it does not freeze the inputs.

Next fix: persist an immutable render manifest when queuing, including ordered scenes, durations, media IDs and render settings, and use it in every segment and concatenation job.

### P1 — Re-export can delete a file referenced by an approval or scheduled post

`api/app/Traits/RendersExportScenes.php::purgePreviousExports` deletes previous output media and clears old export asset IDs for the same project/ratio/language. It does not check approvals or scheduled-post references. Those consumers refer to export-job IDs, so a subsequent export can break their video.

Next fix: retain referenced versions and introduce explicit retention/cleanup rules. Do not delete files merely because a newer export exists.

### P2 — Backend delivery eligibility is incomplete

`api/app/Http/Controllers/Api/V1/Approval/ApprovalController.php::store` checks export ownership but does not require a completed export with an available asset. `Publishing/ScheduledPostController.php::store` requires completed status, but does not require an available output asset. In particular, a completed export whose asset was purged can still pass the scheduling status check.

Next fix: share one server-side eligibility check for ownership, completion and deliverable asset. Reject unavailable versions before creating the approval or scheduled post. Frontend checks are useful UX, not a substitute for endpoint validation.

### P2 — A public link follows the latest export and exposes current draft snippets

`api/app/Http/Controllers/Api/V1/Project/PublicShareController.php::show` selects the latest completed export, while reading snippets directly from current scenes. Unexported script edits can therefore appear below an older video; a subsequent export also changes what the same URL plays. The warning does not turn this into a version-pinned share.

Next fix: pin public delivery links to a specific export and serve metadata from its manifest, or explicitly label links as always showing the latest exported version. Avoid publishing draft text in either case.

### P2 — Visual-style autosave failures appear successful/idle

`web/src/views/EditorView.vue` watchers for `visualStyleDraft` and `customVisualStyleDraft` catch PATCH failures and return their save state to `idle`. A user can believe a style choice was saved when it was not. These settings affect subsequent generation rather than directly changing existing rendered media, but silent failure is still misleading.

Next fix: retain an error state, explain the failed save and provide retry; ensure regeneration waits for persisted style choices.

## Verification

- PHP tests cover fingerprint capture, changes within the same second, scene/script/media/audio/caption/music changes, deleted scenes, metadata-only changes, legacy exports and workspace isolation/unavailable output.
- JavaScript tests cover each action, explicit old-export confirmation, unsaved edits, update-before-action, failed rendering, unavailable exports, cancellation and edits during rendering.
- Existing automatic-finishing and result-screen regression suites are also run.
- Production frontend build passes (existing bundle-size and mixed import warnings remain).
- Chrome with mocked APIs: editor mounts without runtime errors; all five desktop actions show the dialog; dialog fits desktop and mobile widths. No real approval, share, payment, generation or scheduled post was sent.
