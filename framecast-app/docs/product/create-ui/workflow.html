      Examples are explicit scenarios, not model interpretations.
      When something fails or the agent is unsure
      • Before dispatch: invalid inputs, insufficient available credits or an unsupported combination produce a specific fix. Nothing is purchased.
      • Confirmed provider failure: explain the outcome, settle known usage, release unused reservations. A retry or alternative must fit the approved scope and remaining budget.
      • Unknown external outcome: pause and reconcile the existing receipt. Never automatically repeat an uncertain paid call. Preserve earlier outputs and show what is held.
      • Reference mismatch: identify the exact scene or character discrepancy. Repair the affected part; request a new approval if the fix changes the agreed look or exceeds budget.
      • Policy refusal: explain the restriction and offer a supported revision. Do not switch providers to bypass a safety rejection.
      • Review unavailable: label the draft “review incomplete.” Do not claim it passed or silently publish it.
      Tools, reference fidelity, images & delivery
      • App tools inspect reference images and sampled video frames, then request targeted frames where useful. Sampling is not a claim that every pixel or frame has been checked.
      • Brand colours, reference styling and explicit instructions remain distinct. Ask about conflicts; do not automatically paint every reference with the same brand palette.
      • The agent uses Hyperframes through its supported integration and app runner. Remotion is another route only when its adapter is available and suitable. The renderer choice must not become an extra user task.
      • All Replicate generation goes through app-owned tools, approved models, metering and receipts. The agent cannot invent a vendor or execute arbitrary provider calls.
      • Images branch after the plan: approved character if needed → priced image draft → checks → full-resolution image delivery. No video storyboard, audio purchase or video export is required.
      • Download, share and schedule use a specific finished version. If later edits exist, offer “Use the earlier export” or “Update export.” Scheduling and public sharing require their own confirmation.
      What is saved for debugging and recovery
      • Request ID and user message, source hashes, reference observations and unresolved questions.
      • Plan version, approved character hash, storyboard revision, quote and spending approval.
      • Tool name, validated inputs, provider request IDs, status, timings, usage and reservation movements.
      • Review findings, repaired versions, render/export hashes and delivery actions.
      • Record concise decisions and tool evidence, not hidden model reasoning. Credentials stay out of the transcript and diagnostic exports.
      Proposal versus current implementation

      This document describes the intended experience. It does not certify every stage is implemented.

      The current local flow still generates the character master as part of storyboarding. Moving that first preview and its approval before storyboard generation requires a dedicated character-preview stage, persisted approval state and matching quote/recovery handling.

      Inline character review, cost review, shared reservations and request trajectories have local implementations. End-to-end acceptance of the revised sequence, fidelity checks and reliable recovery still needs testing.
